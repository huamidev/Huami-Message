# Huami Message — 产品与技术方案

> 这份文档是项目的"总纲"。每次我们做一个决定，就把它记到这里。
> 你不需要看懂所有技术词，只需要在「待确认」的地方做选择。

---

## 0. 一句话定位

**Huami Message 不是聊天工具，是"帮你把话说好"的工具。**

- 模块一：和真实好友聊天，发送前可以让 AI 把这句话润色得更得体。
- 模块二：聊天页里的「小助手」，帮你分析对方的话、帮你想怎么回。
  它**集成在聊天界面里**，不是独立页面 —— 详见 §2.2。

## 1. 技术选型

### 1.1 总览表

| 维度 | A. Firebase | **B. Supabase（推荐）** | C. CloudKit | D. LeanCloud |
|---|---|---|---|---|
| 要不要自己写后端 | 不用 | 不用 | 不用 | 不用 |
| 实时收消息 | ✅ 开箱即用 | ✅ 开箱即用 | ⚠️ 绕，靠推送订阅 | ✅ 强项 |
| 本地离线消息 | ✅ 自带 | ⚠️ 自己写（SwiftData） | ✅ 自带 | ✅ 自带 |
| 中国大陆可用 | ❌ **不可用** | ⚠️ 一般可连，偶尔慢 | ✅ 走 iCloud | ✅ 最稳 |
| 推送通知 | FCM（国内不可用） | 需自己接 APNs | 自带 | 自带 |
| 免费额度 | 够用 | 够用 | 免费 | 开发版够用 |
| 数据可迁移 | ❌ 私有格式 | ✅ 标准 PostgreSQL | ❌ | ❌ |
| 上手难度 | ★☆☆☆☆ | ★★☆☆☆ | ★★★★☆ | ★★★☆☆ |
| 中文文档 | 一般 | 一般 | 好 | 很好 |

### 1.2 结论

**主线推荐：SwiftUI + Supabase**

理由：
1. 不用租服务器、不用写后端程序。数据库 + 实时消息广播 + 登录系统都是现成的。
2. **不依赖 Google。** Firebase 是 Google 的，中国大陆的 iPhone 直接连不上——这是硬伤不是"慢一点"。
3. 有官方 Swift 库，教程多，AI 也最会写它的代码。
4. 数据库是标准 PostgreSQL，全世界通用。以后想换后端，数据能搬走，不会被锁死。
5. **关键**：AI 的 API Key 可以藏在它的云函数里，不落到 App 里（见 §1.5）。

代价（提前说清）：
- 它**不提供**离线消息和推送通知，这两块要自己搭。可控，但不是小事。
- 国内偶尔连接慢。
- 需要注册账号 + 建几张数据库表（我会带你复制粘贴）。

**备选 D：LeanCloud** — 如果朋友全在国内，且 Supabase 卡到影响体验，就换它。IM 是它的主业，推送和离线消息自带，中文文档。缺点：配置项多、免费版有限制、以后想换要重写。
**A：Firebase** — 技术上最省事，但朋友在国内就用不了。仅当朋友都在海外时才是首选。
**C：CloudKit** — 免费、国内可用，但用它做一对一双人聊天是"用螺丝刀敲钉子"，实时性差、出错难查。不作为主线。

### 1.3 UI 框架：SwiftUI

没有悬念，用 **SwiftUI**。

- 毛玻璃：SwiftUI 里 `一行 .background(.ultraThinMaterial)`；UIKit 要自己管 `UIVisualEffectView` 和层级。
- 动画：SwiftUI 的 `withAnimation` / `.transition` / `.matchedGeometryEffect` 比 UIKit 少写约 70% 代码。
- UIKit 唯一优势是超长列表性能。真到瓶颈了，可以把"消息列表"这一个控件单独换成 UIKit 混写，其余不动。不值得一开始就选它。

### 1.4 本地存储：SwiftData

- 用途：所有消息都存在手机本地。**打开 App 直接读本地 → 瞬间显示 → 后台静默拉新消息。** 这正是"绝不阻塞界面"的实现方式。
- 备选 **GRDB**（SQLite 封装）：更稳更快，聊天类 App 的老牌选择。如果 SwiftData 出怪 bug，就换它，表设计一样，换起来不算痛。
- 不用 Core Data（SwiftData 就是它的接班人）。

### 1.5 AI 调用

- **协议**：统一用 OpenAI 兼容格式。这样换厂商只改一个网址 + 一个模型名。
- **厂商**：主推 **DeepSeek**（国内直连、极便宜、流式简单）；备选 通义千问 / 豆包（国内、已备案，将来上架省事）；Claude / GPT（效果最好但要代理、贵）。
- **流式输出**：SSE。Swift 里用 `URLSession.bytes(for:)` + `for try await line in bytes.lines`，约 30 行代码。

> ⚠️ **安全红线：API Key 绝对不能写进 App 代码。**
> App 包是可以被解开的，Key 会被扒走拿去刷爆你的账户。
> 必须经过一个中转（Supabase 云函数当"传话人"）。
> **第一版就要这么做**，因为它决定了 AI 代码怎么写。

### 1.6 多设备同步（以后再做）

选了 Supabase 基本就白送了：消息本来在云端，任何设备登录同一账号就拉同一份数据。
要额外做的只有"已读位置""草稿"这类状态。第一版不管。

### 1.7 推送通知（以后再做）

- 只能用 **APNs**（苹果官方），FCM 在国内不可用。
- 做法：Supabase 云函数发现新消息 → 调 APNs 接口 → 苹果推到朋友手机。
- 备选 OneSignal（图形化配置、免费额度大），但国内到达率不如直连。
- **第一版不做推送**：App 开着就能收消息，测试够用。

## 2. 产品决策

### 2.1 AI 润色方式（模块一）

| 方案 | 说明 | 优劣 |
|---|---|---|
| 1. 一键改写 | 点一下出一个新版本，可用/撤销 | 最快最好懂；只有 1 个答案，AI 猜错要重来 |
| **2. 多版本候选** | 一次给 3 个：「更得体」「更简短」「更有温度」 | **推荐**：把"AI 的判断"换成"你的选择"，最不容易出错 |
| 3. 滑杆调语气 | 正式↔亲切、简短↔详细，拖动实时重写 | 很酷、有记忆点；实现成本高，普通人不知道拖到哪合适 |
| 4. 意图重写 | 说"我想拒绝他"→ AI 直接写 | 价值感最强；但这是"从零写"，更适合放模块二 |
| 5. 结合上下文 | 读最近 N 条消息再改，效果更好 | **隐私风险最高**，需单独决定，见下 |

**上下文润色的隐私取舍**

- 好处：效果明显更好（知道对方刚失恋，就不会把"那挺好的"改得轻佻）。
- 风险：**你和朋友的聊天记录会离开你的设备，发到 AI 厂商服务器。** 这既是用户信任问题，也是审核关注点。
- **建议**：默认**关闭**；提供明确开关；开启时用一句话说明"最近 10 条消息将发送给 AI 服务商处理"；界面上持续显示一个小标记，让用户随时知道现在是"会读上下文"的状态。
- 理由：不读上下文也能把润色做得不错。一旦默认读上下文，产品就变成"你的私聊会被上传"，这是重资产。

### 2.2 AI 好友用途（模块二）

| 方案 | 场景 | 评价 |
|---|---|---|
| **A. 关系军师** | 对方一句话让你不舒服，你贴给 AI，它分析 + 给 2-3 个回复方向 | **推荐主功能** |
| **B. 起稿助手** | 要发重要消息（道歉/表白/请假/拒绝/催款），告诉它意图和关系，它写初稿 | **推荐，和 A 合并** |
| C. 模拟对话练习 | 明天要跟老板谈加薪，先跟 AI 演练，它扮演对方并给反馈 | 独特、Demo 惊艳；第二步再加 |
| D. 通用陪聊 | 就是聊天 | ❌ **不推荐做主卖点**，见下 |
| E. 关系复盘 | 贴一段对话，总结你们的沟通模式 | 有价值但低频，隐私最敏感，以后再说 |

**为什么不做 D（通用陪聊）**：等于"又一个 ChatGPT 套壳"，App Store 审核很容易按 4.3（重复/垃圾应用）打回；而且它和产品定位相反——"帮你把话说好"变成了"帮你不用跟人说话"。

**A 和 B 怎么分工**：A 是"事后救火"，B 是"事前准备"。同一个入口里放两个按钮（`帮我回` / `帮我起稿`），逻辑清晰。

**模块一 vs 模块二 的界限**（必须保持分开）：
- 模块一 = **修**。就地改你正在打的这一句话。轻、快、单句、上下文可选。
- 模块二 = **想**。独立对话，可以长篇、多轮、贴对话、扮演角色、长期记忆。

**命名建议**：不要叫「AI 好友」，叫 **「军师」**。
- 叫"AI 好友"会让人以为是陪聊 → 预期错位，审核也更容易觉得是套壳。
- 叫"军师"直接说明用途，强化"帮你把话说好"的定位。

## 3. 开发路线图

原计划：1) 真实好友发消息 → 2) AI 润色 → 3) AI 好友 → 4) 毛玻璃
**调整后**：**0) 界面外壳 + 假数据（含毛玻璃基调）** → 1) 真实好友通信 → 2) AI 润色 → 3) AI 好友 → 4) 打磨

**为什么要在最前面插"第 0 步"**：

1. 毛玻璃不是"最后刷的一层漆"，它是**布局方式**。`.ultraThinMaterial` 只有在"有内容从它下面滚过去"的层级里才有质感——这决定了你的视图层级怎么搭。等 4 个功能都做完了再改层级，等于重写。
2. 假数据阶段能 100% 专注动画和手感，改一行看一眼效果。这是新手最容易获得成就感、也最容易学明白的阶段。
3. 反过来，一上来做后端要先注册服务、配数据库、学网络请求，可能两天看不到任何画面，容易放弃。
4. **但最多 2-3 天**。真正会卡住你的是后端和审核，UI 不是风险点。
5. 关键技巧：第 0 步就把**数据层抽象**做好，之后把假数据换成真数据时，UI 代码一行都不用改。

## 4. TestFlight 准备清单

### 4.1 今天就能做（不用写代码）

- [ ] **注册 Apple Developer Program**：$99/年（中国区 ¥688/年）。审核通常 24-48 小时，有时更久。**这是最长的等待项，先启动。**
  - 个人身份注册时，你的**法定姓名会显示在 App Store 开发者栏**。想隐藏真名要注册公司账号（需邓白氏编码，麻烦得多）。TestFlight 阶段无所谓。
- [ ] **建 App Store Connect 记录**：App 名称、Bundle ID。
- [ ] **准备 3 样审核物料**：
  - 隐私政策 URL（必须）。可先用免费 GitHub Pages。**必须写明**：收集哪些数据、AI 润色时是否会把消息发给第三方。
  - 一个可用的测试账号（有登录功能的 App 必须给审核员能直接登录的账号，否则必被拒）。
  - App 图标 1024×1024。
- [ ] **想清楚朋友的手机系统版本**（决定部署目标，见 §5）。
- [ ] **提前想好内容审核方案**：举报入口、拉黑、内容过滤、零容忍用户协议（见 §6）。

### 4.2 TestFlight 机制（心里有数）

| | 内部测试员 | 外部测试员 |
|---|---|---|
| 人数上限 | 100 | 10,000 |
| 需要苹果审核 | ❌ 不需要 | ✅ 需要 Beta App Review |
| 审核时长 | — | 通常 1-2 天（比正式上架宽松很多） |

- 每个 Build **有效期 90 天**，过期要重新上传。
- **最快路径**：先用内部测试员（你自己 + 1 个朋友）验证 → 再开外部测试。
- 需要填 `Test Information`（测试说明、反馈邮箱）和出口合规声明（见 §5）。

## 6. 隐私与审核红线

### 6.1 硬性要求（App Store 审核必查）

- **1.2 用户生成内容**：只要有用户互发消息，就必须有 ①举报入口 ②拉黑功能 ③内容过滤 ④零容忍用户协议。TestFlight 阶段相对宽松，但建议第一版就留好位置。
- **5.1.1 隐私**：App 内可删除账号；隐私政策 URL；App Store Connect 里填"隐私营养标签"。
- **4.8 登录**：如果提供第三方/社交登录，就必须同时提供"通过 Apple 登录"。
- **好友发现方式**：**不要上传通讯录**（隐私雷区 + 审核风险）。用**邀请码 / 二维码 / 用户名搜索**。

### 6.2 中国大陆上架的额外门槛（TestFlight 阶段不涉及）

- **ICP 备案**：2023 年 9 月起，在中国大陆 App Store 上架的 App 需完成工信部 App 备案。
- **生成式 AI 备案**：按《生成式人工智能服务管理暂行办法》，提供生成式 AI 功能需做算法/服务备案，通行做法是接入**已备案的国内大模型**（豆包、通义等）。
- **影响**：给朋友 TestFlight 测试**完全不受影响**。但若将来要正式上国区，这一条会决定你选哪家 AI 厂商——**这也是 AI 层必须做成"可换厂商"的原因**。
- 参考：[生成式人工智能服务管理暂行办法（国务院公报）](https://www.gov.cn/gongbao/2023/issue_10666/202308/content_6900864.html)、[TestFlight 概述（Apple）](https://developer.apple.com/cn/help/app-store-connect/test-a-beta-version/testflight-overview/)

## 7. 已确认的产品与技术决策

（2026-10-08 确认）

| 决策项 | 结论 | 备注 |
|---|---|---|

这条边界不只是产品逻辑，也是**过审逻辑** —— 审核员要能一眼看出，
这不是「微信 + 一个 ChatGPT 按钮」。

## 9. 视觉风格（当前）

**浅色 + 干净 + 以内容为主**，参考 TIM：

- 浅灰底 `#F2F3F5` + 白卡片 `#FFFFFF`，层次靠明度对比而不是模糊发光
- 单一主色 `#12B7F5`，只用在按钮、未读、自己的气泡上
- 文字分三级（`#1A1A1A` / `#5A5F66` / `#9AA0A6`）
- 头像为圆角方形（TIM/QQ 的风格），不是圆形
- 阴影只给真正悬浮的元素（输入栏），且"大而淡"
