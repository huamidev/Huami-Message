# 丝滑打磨：修掉 3 个真 bug + 加手感

> 这一轮不加功能，只做**你最开始定的最高优先级**：「像 Telegram 一样丝滑」。
> 复查代码 + 长列表自检的过程中发现了 3 个真 bug。

---

## 一、修掉的 3 个 bug

### bug 1：新消息会把正在读旧消息的你「猛地拽到底部」⭐

**现象**：往上翻长对话时，只要来一条新消息，画面就被强行拉到最底下。
读长对话根本没法往上翻。

**根因**：代码里是「只要有新消息就无条件滚到底部」，从没考虑过用户当前在看哪里。

**修法**：用 iOS 18 的 `onScrollGeometryChange` **实时知道自己离底部有多远**，
只在「贴着底部」时才自动滚。用户正在往上翻时，界面**安静地待在原地**，
只在一个小按钮上提醒「下面有几条新的」。

这也是 Telegram 和微信的做法 —— 它们让「往上翻」变成一个**安全的动作**：
你知道新消息不会跑掉，界面也不会把你踢回去。

### bug 2：消息的弹入动画**从来没生效过**

`MessageBubble` 里写了 `.transition(...)`，代码看着没问题，但一直是"啪"地直接出现。

**根因**：**只定义 `.transition` 而没有动画驱动，等于没写。**
必须有一个 `.animation(_:value:)`（或者包在 `withAnimation` 里）才会真的播出来。

**修法**：在消息列表上加 `.animation(.snappy(duration: 0.26), value: messages.count)`。

> 通用经验：SwiftUI 里 `transition` 是「变化时该怎么演」，`animation` 是「谁来触发演出」。
> 两个都要有，少一个就静悄悄地什么都不发生。

### bug 3：打开长会话时**没有停在最新一条**

**现象**：打开一个有几十条消息的会话，最后两条看不见，还得手动往下滑一下。

**根因**：`LazyVStack` 一开始只"实现"了一部分内容，
`.defaultScrollAnchor(.bottom)` 是按**当时**的内容高度锚的；
随着更多内容被实现、总高度变大，位置就偏了。

**修法**：等布局稳定 280 毫秒后，**不加动画**地补一次滚到底。
（加动画的话，用户会看到打开瞬间画面"唰"地跳一下。）

## 二、加的东西

### 1. 「回到最新」

只在用户往上翻时出现，带一个数字告诉他下面还压着几条没看。
平时完全不存在 —— **需要它的时候它才在**。

### 2. 触觉反馈（震动）

| 动作 | 手感 |
|---|---|
| 发送消息、点「回到最新」 | 轻点 |
| 在几个选项里挑一个（润色风格、助手建议） | 细分的选择感 |
| AI 分析跑完 | 成功 |
| 删除、清空、拉黑、举报 | 警告 |

三条原则写在 [Haptics.swift](../Huami%20Message/Support/Haptics.swift) 里：
**只给"用户做了某件事"的时刻反馈，不给"正在发生"的时刻**（每来一条消息就震一下，
用户会想卸载）；**强度要克制**；**成功和失败必须能分辨**。

> ⚠️ **模拟器没有震动马达，这些调用是空操作 —— 必须装到真机上才能感觉到。**

### 3. 底部渐隐

让消息在接近输入栏时"淡淡地没掉"，而不是被一条硬边切断。

## 三、一个用「红色探针」查出来的布局问题

修完上面那些之后，截图里发现：**消息从「输入栏底部」和「悬浮标签栏」之间的缝里露出来了**。

iOS 26 的标签栏是一个**悬浮胶囊**，它背后不垫任何东西，
所以滚到底部的消息会从输入栏下方的区域露出来，看着像排版坏了。

我先试了 `.ignoresSafeArea(edges: .bottom)` —— **没用**。
为了搞清楚到底画在哪，我把渐隐层临时换成**纯红色、300 磅高**，截图量了一下：

> 它的底边老老实实停在安全区底边（约 800 磅），**下面还有 74 磅盖不住**。
> 也就是说：**`.ignoresSafeArea()` 在 ZStack 的底部对齐子视图里不生效。**

正确做法是用 `background` 的 `ignoresSafeAreaEdges` 参数 —— 这个参数就是为这种事准备的：

```swift
.background(Theme.background, ignoresSafeAreaEdges: .bottom)
```

**教训**：布局出问题时不要靠猜。**把可疑的那一层临时涂成刺眼的颜色，截图量一下**，
比读十遍文档都快。

## 四、怎么验证的（可复现）

交互行为截图看不出来，所以我加了一个「自检场景」：
**先灌 60 条填充消息把列表撑长 → 滚到最顶 → 再发一条消息**。

```bash
B=com.huamidev.HuamiMessage
xcrun simctl launch booted $B -openChat 1 -seedMany 60 -verifyScrollFix 1
```

**正确表现**：画面**停在原地**（还显示着最老的几条），
左下角出现「回到最新 ②」（我发的那条 + 对方的自动回复）。

如果画面被拽到了底部，就说明修复没生效。

`-seedMany` 还有个附带好处：**5 条消息的列表是测不出性能问题的**，
60 条才看得出滚动和布局有没有毛病（bug 3 就是这么发现的）。
