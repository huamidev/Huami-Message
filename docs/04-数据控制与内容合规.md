### 为什么举报面板里要写"我们会怎么处理"

App Store 指南 1.2 条不只要"有一个举报按钮"。它要求：

1. 有举报入口 ✓
2. 有拉黑功能 ✓
3. **说明举报之后会发生什么** ← 很多人漏掉
4. **零容忍条款**（写明什么内容会被处理）← 很多人漏掉

所以举报面板底部专门有一块「我们会怎么处理」，写明：零容忍哪些内容、
24 小时内处理、核实后封号、可以同时拉黑、举报记录会保留。

> **经验：合规要求不是"加个按钮"，而是"让审核员能确认这套机制是真的"。**
> 藏在几层菜单里的举报入口，和不写处理承诺的举报按钮，都可能被拒。

## 二、抓到的 bug：删除被后台同步"复活" ⭐

这是本地优先架构里**最经典的一类坑**，而且它直接决定了以后接 Supabase 时删除功能能不能用。

### 现象

删掉会话「林一」之后查数据库：

```
删除前：4 个好友 / 15 条消息
删除后：4 个好友 / 12 条消息      ← 好友没删掉！消息也只少了 3 条
```

### 根因

同步分不清这两种情况：

- 「这台设备从没见过它」 → 应该拉下来
- 「用户故意删了它」 → **绝不能拉回来**

于是后台同步一跑，就把服务器上还存在的「林一」又拉回来了。

### 解法：删除墓碑

**删除不是"抹掉"，而是"记下它被删过"。**

新增一张 `StoredTombstone` 表：删东西的时候顺手记一笔"这个 id 被删了"。
同步时看到墓碑就跳过。

接上 Supabase 之后，墓碑还要多一个作用：**把"我删了它"同步到服务器**。
否则你在这台手机上删了，换台设备登录，删掉的东西又回来了。
（等服务器确认删除之后，墓碑才能清掉，不然会越积越多。）

### 验证（可复现）

```bash
B=com.huamidev.HuamiMessage
# 删除林一，然后重启 3 次
xcrun simctl launch booted $B -openChat 1 -devDeleteChat 1
```

| | 好友 | 消息 | 墓碑 |
|---|---|---|---|
| 删除前 | 4 | 12 | 0 |
| 删除后 | 3 | 7 | 6 |
| **再重启 3 次** | **3** | **7** | 6 |

✅ 林一没有复活。

## 三、一个重要的好消息：数据库结构能自动升级

这一步给数据库加了新字段（`isBlocked`）和两张新表（举报、墓碑）。
我特意验证了**旧数据会不会因此丢掉**：

| | 升级前 | 升级后（结构已变） |
|---|---|---|
| 消息 | 15 条 | **15 条** ✓ |
| 好友 | 4 个 | **4 个** ✓ |
| `isBlocked` 字段 | 不存在 | 自动加上 ✓ |
| `StoredReport` 表 | 不存在 | 自动建好 ✓ |

**这意味着以后给 App 加字段，用户升级时聊天记录不会丢。**

能自动升级的关键是那条经验：**给新增的字段留一个合理的默认值**
（`var isBlocked: Bool = false`）。没有默认值，数据库就不知道该给老数据填什么，
只能失败。

> ⚠️ 但这条路不是无限的：如果以后要做"改字段名""拆表"这类**破坏性**改动，
> 就必须自己写迁移逻辑。到那一步我会提前提醒你。

## 四、顺手修的小问题

**拉黑提示条出现时，最后一条消息被输入栏挡住。**
原因是提示条改变了聊天区域的高度，而列表没有重新对齐到底部。
修法是监听拉黑状态变化，主动滚一次到底。

这类问题不大，但"最后一条看不见"是用户一眼就能察觉的毛病 ——
**打磨就是由这些一眼可见的小事堆起来的。**

### 关于"会话列表改用 List"

原来用的是 `ScrollView` + `LazyVStack`。这一步换成了 `List`，因为
**`.swipeActions`（左滑操作）只在 List 里生效**，自己手写一套滑动手势
既费劲又做不跟手。

代价是 List 自带白底和分隔线，会毁掉毛玻璃效果。用三行关掉就行：

```swift
.scrollContentBackground(.hidden)   // 关掉列表自己的背景
.listRowBackground(Color.clear)     // 关掉每一行的背景
.listRowSeparator(.hidden)          // 关掉行之间的分隔线
```

关掉之后，List 就变成一个"支持左滑的透明容器"，底下的极光照常透出来。
