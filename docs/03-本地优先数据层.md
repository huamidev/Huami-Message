# 第 1 步（上）：本地优先数据层 + 发送状态

> 这一步没有联网、没有服务器，但它是**你最看重那条需求的全部实现**：
> 「打开 App 瞬间就能操作，历史消息后台静默同步，绝不阻塞界面」。
>
> 做完之后，消息**杀掉 App 也不会丢**了。

---

## 一、这一步解决了什么问题

在这之前，消息只存在内存里 —— **杀掉 App 就全没了**，打开也是空的。
现在：

| 能力 | 状态 |
|---|---|
| 消息存进手机本地数据库 | ✅ 杀掉 App 再打开，消息还在 |
| 打开 App 立刻能用（不等网络） | ✅ 界面只读本地，同步在后台跑 |
| 完全没有网络也能用 | ✅ 可验证（见第四节） |
| 发送中转圈 → 已发送 | ✅ |
| 发送失败 → 红色重试按钮 | ✅ 而且失败的消息也会存下来 |
| 同一会话不会重复存消息 | ✅ 重启三次消息数不变 |

## 二、核心思路：界面永远只等本地，永远不等网络

```
        ┌─────────────────────────────────────┐
        │            ChatStore                │
        │         （消息模块总管家）            │
        └──────────┬───────────────┬──────────┘
                   │               │
         ①同步读、几毫秒      ②后台慢慢跑
                   │               │
        ┌──────────▼──────┐  ┌─────▼──────────────┐
        │  local 本地数据库 │  │ remote 服务器       │
        │   （SwiftData）  │◄─┤ （现在是假数据，     │
        │                 │  │   以后是 Supabase）  │
        └──────────┬──────┘  └────────────────────┘
                   │
        ┌──────────▼──────┐
        │   界面（View）    │
        └─────────────────┘
```

打开 App 的顺序（**这个顺序就是「丝滑」的全部秘密**）：

1. `start()` 先**同步**读本地（几毫秒）→ 界面立刻铺满内容，用户马上能操作
2. 然后才去后台拉服务器（可能要几秒）→ 拉到什么补什么
3. 网络慢、网络断了，界面**完全不受影响**

顺序反过来的话（先等网络），App 打开就会转圈 —— 那是所有「卡顿感」的来源。

### 为什么"本地读取"故意写成同步的

`LocalStore` 协议里所有方法都**没有 async**。这不是偷懒：

**本地读取必须"立刻返回"，一秒都不能等。**
一旦写成 async，就会冒出转圈和闪一下，那就不是瞬间可用了。

## 三、这一步踩的两个真 bug（都很有价值）

### bug 1：假数据的 id 每次启动都变 → 消息重复入库

我原来用 `UUID()` 生成假数据的 id。单次运行完全正常，
但**每开一次 App，数据库里就多一份重复的「在吗」** —— 开三次就有三份。

这个 bug 很隐蔽：不重启就永远发现不了。而真服务器上每条消息的 id
都是服务器生成的、永远不变，所以「用固定 id」反而更接近真实。

顺带还写错了一次 UUID 格式（多写了一组，变成 41 个字符而不是 36），
`UUID(uuidString:)` 返回 nil，被 `!` 强制解包当场崩溃。
**崩溃栈非常明确，一眼就指到了出错那一行** —— 这就是"宁可崩得清清楚楚，
也不要错得莫名其妙"。

### bug 2：后台同步把用户刚发的消息状态冲掉了 ⭐

这个是真架构问题，**接上 Supabase 之后一定会遇到**。

日志里的时序：

```
15:42:52.278  deliver 进入                       ← 用户发消息
15:42:52.446  deliver 写入 status=sent           ← 发送成功
15:42:52.499  db.save 更新已有行 status=sending   ← 后台同步把旧的又写回来了！
```

**根因**：本地优先架构有个必然的副作用 —— 界面在「读本地」那一步就已经可用了，
而「后台同步」还在跑。用户完全可能在同步没结束时发出一条消息，
这时同步拿着服务器上的旧版本往下盖，就把本地刚写好的「已发送」覆盖回「发送中」。

**真机上比模拟器严重得多：网络越慢，撞车窗口越大。**

**修法**：给「服务器来的数据」单独定一条合并规则，写在
[LocalStore.swift](../Huami%20Message/Persistence/LocalStore.swift) 里：

> **本地还处于「发送中 / 发送失败」的消息，一律以本地为准，不许被服务器覆盖。**

对应两个方法：`save()`（本地产生的）和 `saveFromRemote()`（服务器来的）。
把"合并策略"收在数据层里，界面和 ChatStore 都不用操心。

> **通用经验：只要做了"本地优先 + 后台同步"，就一定有这个竞态。
> 必须提前想好"谁覆盖谁"的规则，不能等出了 bug 再补。**

## 四、怎么证明它真的能用（可复现）

我加了几个调试开关，你随时可以自己验一遍：

```bash
B=com.huamidev.HuamiMessage

# 1) 正常启动一次，让数据写进本地数据库
xcrun simctl launch booted $B

# 2) 完全离线启动 —— 还能看到全部历史，就证明界面真的不依赖网络
xcrun simctl launch booted $B -offline 1

# 3) 自动发一条消息（验证"发送 → 存库 → 重启还在"）
xcrun simctl launch booted $B -openChat 1 -autoSend 1

# 4) 自动发一条必定失败的消息（验证失败状态和重试按钮）
xcrun simctl launch booted $B -openChat 1 -autoSend 1 -failSend 1
```

还可以直接看数据库文件：

```bash
DATA=$(xcrun simctl get_app_container booted com.huamidev.HuamiMessage data)
sqlite3 "$DATA/Library/Application Support/default.store" \
  "SELECT substr(ZTEXT,1,30), ZSTATUSRAW FROM ZSTOREDMESSAGE;"
```

## 五、新增/改动的文件

```
Huami Message/
├── Persistence/                  ★ 新增：本地数据库这一层
│   ├── StoredModels.swift        @Model 档案（和界面的 struct 是两套，故意的）
│   ├── LocalStore.swift          本地库的「插座标准」+ SwiftData 实现
│   └── AppDatabase.swift         数据库的创建（失败退化成内存模式，不崩）
│
├── Models/ChatModels.swift       加了 MessageStatus（发送中/已发送/失败）
├── Stores/ChatStore.swift        改成本地优先：先读本地，再后台同步
├── Services/MockChatService.swift 固定 id + 可强制失败
├── Support/DevFlags.swift        加了 -offline / -autoSend / -failSend
├── Huami_MessageApp.swift        建数据库、注入 ChatStore
└── Features/Messages/MessageBubble.swift  显示发送状态 + 重试按钮
```

### 为什么 `@Model` 档案和界面的 struct 要分成两套

- `ChatModels.swift` 里的 struct —— 界面用的、在代码里传来传去的「数据包」
- `Persistence/StoredModels.swift` 里的 @Model class —— 真正躺在数据库文件里的「档案」

分开是因为：数据库的写法（表结构、字段、索引）会变，而界面不该关心这些。
分开了以后，**改数据库结构不用动界面一行代码**。

这跟 `ChatService` 那道「插座防火墙」是同一个思路：
**每一层只跟自己那一层的邻居打交道。**

## 六、这一步"故意没做"的

| 没做 | 为什么 |
|---|---|
| 真的服务器 | 下一步接 Supabase。现在的 `remote` 还是假数据 |
| 本地消息分页 | 消息量小的时候，全读出来反而更简单更稳。几万条时才需要优化 |
| 数据库结构升级（迁移） | 现在改结构会导致旧数据读不出来。开发期可接受（会退化成内存模式并打日志），**上架前必须处理** |
| 已读回执、正在输入 | 属于"锦上添花"，等核心链路稳了再说 |
