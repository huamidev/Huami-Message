# 接上 Supabase：真的登录，和一套「假服务器」验证法

> 这一轮把 Supabase 的客户端真正写出来了。
> 而且做了一件之前几轮做不到的事：**在没有真账号的情况下，验证了代码是对的。**

---

## 一、一个开关：填进去就变成真的

从第一轮开始，聊天、AI、登录背后都是假数据。但我不可能在你有账号的那天，
把几十个文件全改一遍。

所以做成了一个开关：

```
没有 Secrets.plist   →  假数据（演示模式，界面上有明确标识）
有 Secrets.plist     →  真服务器
```

**不用改任何界面代码，也不用改调用方。** 你只要把文件填好。

### 你要做什么

在 `Huami Message/` 目录下建一个 `Secrets.plist`：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>SUPABASE_URL</key>
    <string>https://你的项目.supabase.co</string>
    <key>SUPABASE_ANON_KEY</key>
    <string>eyJhbGciOi...</string>
</dict>
</plist>
```

这个文件已经在 `.gitignore` 里，不会被提交。

> ⚠️ **绝对不要把 service_role key 填进去。**
> 那把钥匙能绕过所有权限规则读写整个数据库，放进 App 等于把门钥匙贴在门上。

## 二、为什么不用官方的 supabase-swift

算过一笔账：

- 官方 SDK 要加一个 SPM 依赖，会拉下来几十个包、几百 MB
- 而我们其实只用到两件事：一个 REST 接口（GET/POST）和一个 WebSocket
- 自己写还能顺手把错误信息翻成人话

**代价**：官方的便利功能要自己写（比如自动刷新 token）。第一版用不上。

写出来大约 400 行，包括一个 HTTP 客户端和登录服务。

## 三、登录凭证存在系统钥匙串，不是 UserDefaults

这是这一轮里最重要的一个安全决定。

`UserDefaults` 存在 App 容器里的一个 plist 文件里，而那个文件会
**跟着 iTunes / iCloud 备份一起走**。备份不加密的话，换台电脑就能看到里面的字符串。

登录凭证泄露 = 别人可以冒充你、读你所有消息。所以必须放钥匙串。

### 但我在测试环境里发现它写不进去

```
钥匙串写入失败：-34018
```

`-34018` 是「缺少权限」。原因是我一直在用**关闭签名的构建**做测试
（`CODE_SIGNING_ALLOWED=NO`），这种包没有 entitlements，钥匙串不可用。

我试过手工加上 entitlement 重新签名（还试了带团队 ID 前缀的版本），都没解决 ——
模拟器要求的是真实签名身份。

**这个坑本身是测试环境的，正式签名后不会有。** 但它暴露了一个产品问题：

> **如果钥匙串写不进去，App 会照样能用，只是每次打开都要重新登录。**
> 让用户自己发现"怎么老是要我登录"是最差的做法。

所以加了如实告知：登录页和个人页会显示
「⚠️ 这台设备上没能保存登录状态，下次打开需要重新登录」。

**没能验证的部分我也说清楚**：会话的存取（钥匙串那 30 行）在正式签名前
我无法自动验证。但它写不进去时的降级路径验证过了（重启回到登录页 ✓）。

## 四、起一个「假 Supabase」来验证客户端

这是这一轮最有价值的做法。

写 Supabase 客户端时有个两难：

- 不连真的，就没法验证代码（"写完就交"等于把 bug 留到以后）
- 连真的，又得先注册账号

**解法：按真实 API 的形状起一个本地假服务。**

`tools/fake-supabase/server.py` 实现了四个接口：

| 接口 | 用途 |
|---|---|
| `POST /auth/v1/signup` | 注册（重复注册返回真实的 422 文案） |
| `POST /auth/v1/token?grant_type=password` | 登录（密码错返回真实的 `invalid_grant`） |
| `POST /auth/v1/logout` | 退出 |
| `GET /rest/v1/profiles` | 读用户档案（模拟数据库触发器建好的那条） |

App 用启动参数连它：

```bash
xcrun simctl launch booted com.huamidev.HuamiMessage \
  -supabaseURL http://127.0.0.1:54321 -supabaseKey test
```

### 它抓到了什么

假服务器把 App **真实发出的请求**全记下来了：

```
POST /auth/v1/signup
  apikey: test                          ← 登录前用 anon key
  authorization: Bearer test
  body: {'email': 'test@huami.app', 'password': '***'}
  → 200 注册成功，档案邀请码 93JZJPYZ

GET /rest/v1/profiles?select=*&id=eq.082f7ce1-…&limit=1
  authorization: Bearer fake-access-t…  ← 登录后自动换成用户凭证 ✅
  → 200 档案 display_name=test
```

**注意第二行**：登录成功后，请求头里的凭证自动从 anon key 换成了用户的 access token。
这正是服务器权限规则（RLS）能生效的前提 —— 服务器靠它知道"你是谁"。

然后 App 界面上显示的昵称、头像色、邀请码 `93JZJPYZ`
和服务器日志里的完全一致 ✓ —— **不是本地假数据，是真的从"服务器"拿的。**

### 这个方法验不了什么

- 真实 Supabase 的行为细节（版本差异、边界情况、RLS 到底拦不拦得住）
- 钥匙串（见上面）

那些只能等接上真的才知道。但比"写完就交"强太多了。

## 五、顺手抓到一个真问题：隐私说明和行为对不上了

我在看截图时发现，「我」页上写着：

> 只有你主动点开小助手、**并再点一次**「帮我看看怎么回」时，才会把最近 10 条消息发给 AI

但小助手改版之后（见 [13-小助手决策模型.md](13-小助手决策模型.md)），
**点一下选项就直接发送了** —— 没有第二步。

**隐私说明和行为不一致，既误导用户，也是审核会抓的问题。**

而且它散落在四个地方：App 内两个 + 法务文本两处。

改法：法务文本是唯一事实来源（App 内和网页版都从它生成），所以改一处，
重跑 `python3 tools/build-legal-html.py`，两边一起更新。

### 改的时候我又踩了同一个坑

我在 Swift 字符串里用了 **ASCII 双引号**：

```swift
"……一直标明"点选项会把最近 10 条消息发给 AI"，判断结果里……"
```

字符串被从中间截断。**这是我第二次踩这个坑**（第一次在举报面板）。

编译器能抓到，但**生成器在编译之前就跑了** —— 它会安静地产出一个
"中间缺一块"的网页，看起来还挺正常。

所以给生成器加了一道检查：**中文之间出现连续 4 个以上空格**，
基本就是截断留下的痕迹。

> 加这道检查本身也有个教训：我第一版的正则只认"空格后面还是汉字"，
> 而实际断裂处后面是**中文逗号**（全角符号，不在汉字编码区），
> 所以检查**没起作用但看起来像起作用了**。
> 我故意造了一个断裂内容去测，才发现它没拦住。
>
> **检查也要被检查。** 一个从没失败过的检查，可能只是永远返回成功。
