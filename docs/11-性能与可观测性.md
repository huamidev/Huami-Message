# 性能：把「打开就有内容」做实

> 这一轮没有加功能，处理的是一件**当时看不出、以后一定会出问题**的事。
>
> 我在早先的代码里留过一句注释：
> 「消息量大到几万条时确实要改成 predicate，那是个明确的优化点，
> 我会在真的需要时才做」——现在就是该做的时候。

---

## 一、问题：一个平方级的坑

原来的写法是「**把整张表捞出来，再在内存里筛**」：

```swift
// 旧写法
fetchAll(StoredMessage.self).filter { $0.friendID == friendID }
```

只有几十条消息时完全看不出问题。但它是个**平方级的坑**：

- 会话列表要给**每一个好友**查一次"最后一条消息"
- 于是 N 个好友 × M 条消息 = **N×M 次比较**

消息一攒起来，打开 App 就会明显变慢 —— 而「打开就有内容」
是用户定的**最高优先级**。

### 实测（5000 条消息）

| 操作 | 优化前 |
|---|---|
| 批量写入 5005 条 | **10895.9ms** |
| 本地读取 5012 条 | （测过一次，也在全表扫的路径上） |

那个 10895.9ms 是在**主线程**上跑的 —— 等于界面卡住将近 11 秒。
这直接违反了「绝不阻塞界面」。

---

## 二、修法：两处改动

### 1. 查询下推到数据库

全部改成 `#Predicate`（数据库层的查询条件）+ 按需 `fetchLimit`，
让数据库自己用索引去查：

```swift
let descriptor = FetchDescriptor<StoredMessage>(
    predicate: #Predicate { $0.friendID == friendID },
    sortBy: [SortDescriptor(\.sentAt, order: .forward)]
)
```

「最后一条消息」尤其关键 —— 它是**每个好友都要调一次**的：

```swift
// 按时间倒序取第一条，而不是"全读出来再找最大的那个"
descriptor.sortBy = [SortDescriptor(\.sentAt, order: .reverse)]
descriptor.fetchLimit = 1
```

### 2. 不再逐条查「这条消息在不在」

这是那 10.8 秒的真正来源。原来每写一条消息都要查一次数据库：

```swift
// 旧逻辑：5000 条 = 5000 次查询
if let existing = findMessage(message.id) { ... }
```

改成**先把"已经存在的消息 id"一次查出来**。首次同步时绝大多数都是新消息，
于是剩下的一律直接插，一次都不用查。

### 3. 分批落盘

一次提交 5005 条，实测主线程会卡住约 **180 毫秒**（差不多 11 帧）。
拆成每 400 条提交一次，单次卡顿降到十几毫秒 —— 滚动时基本感觉不出来。

---

## 三、结果

| | 优化前 | 优化后 | |
|---|---|---|---|
| 批量写入 5005 条 | 10895.9ms | **173.9ms** | **63 倍** |
| 单次主线程卡顿 | ~180ms | **~6–20ms** | 一帧多一点 |
| 本地读取 5012 条 | — | **52.4ms** | 打开 App 的速度 |

52 毫秒打开一个有 5000 条消息的会话 —— 用户感觉不到等待。

---

## 四、方法：把耗时拆开量

优化能这么快找到瓶颈，靠的是**分项计时**：

```
批量写入 5005/5005 条（分 13 批）｜预读 2.7ms｜插入+落盘 173.9ms｜最后一批落盘 6.0ms
```

如果不拆，只能看到一个「10895.9ms」的总数，那就只能靠猜。
拆开之后一眼就看出：**预读 2.8ms、插入 21.7ms、落盘 178.8ms** ——
10.8 秒根本不在这三项里，说明它全花在循环里那些看不见的逐条查询上。

> **通用经验：性能问题不要猜。把耗时拆成几段分别计时，
> 瓶颈通常不在你以为的地方。**

## 五、日志换成了系统的 `os.Logger`

前面几轮排查问题时我吃过一个亏：**`print` 的输出在模拟器里抓不到**
（沙盒不允许开 pty），只能临时往文件里写，排查完还得记得删掉。

换成 `os.Logger` 之后，一条命令就能读：

```bash
xcrun simctl spawn booted log show --last 60s --info \
  --predicate 'subsystem == "com.huamidev.HuamiMessage"' --style compact
```

**踩到的一个坑**：不加 `--info` 读不到。
`Logger.info` 是 INFO 级别，**默认不落盘**，只在内存里转一圈。
要事后能查，得用 `notice` 级别（`log show --info` 也能读）。

另外，工程开了「成员导入可见性」检查，
直接把 `Logger` 暴露出去会让每个写日志的文件都得加 `import OSLog`。
所以把 Logger 关在 `AppLog` 里面，外面只看见一个普通函数：

```swift
AppLog.info(.data, "本地读取：\(n) 个会话，耗时 \(ms)")
```

## 七、一个我自己的教训

改这一轮的时候，我用脚本做代码替换，**有一次把文件切坏了**。

原因是我用 `str.index("...")` 找切片锚点，而它返回的是**第一次出现的位置** ——
锚点文字恰好也出现在协议声明里，于是切片范围反了，
文件被拼成了乱码。

**两条改进，已经用在后续的所有替换里：**

1. 切片前先确认锚点**唯一**（或者从指定位置往后找）
2. **每次替换后必须断言**"确实替换成功了"

第二条尤其重要：这一轮还有一次替换是静默失败的
（锚点写错一个字），脚本没报错就打印了「成功」，直到编译时才暴露。

> **没有断言的自动化，等于没有自动化。**
